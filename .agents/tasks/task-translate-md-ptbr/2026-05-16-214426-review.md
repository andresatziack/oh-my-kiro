## High-level view

The mechanical preservation contract is intact. Fenced code blocks, skill front-matter, URLs, the `## [keyword,...]` section headers parsed by `context-enrichment.sh`, and the `YYYY-MM-DD | status | ...` entry lines parsed by `auto-capture.sh` all match `main` byte-for-byte. Test counts hold at baseline.

Where the pass slips is at the EN/CN boundary. The translator helper, `translate_md.py`, scrubs em dashes on every line it touches regardless of language, which mutates Chinese-only headings (Rule 10 says preserve, the helper deletes). Separately, one file's Chinese parentheticals were rewritten in Portuguese rather than preserved, and 5 plan H1 titles with `# English — Chinese` patterns had their Chinese half rewritten. Same class of error in three different shapes.

Quality on the prose-translated files is solid: README, EXTENSION-GUIDE, agent prompts, command files, and the FEAT-002/FEAT-003 batch read naturally in pt-BR, hold "você" consistently, and respect the consecrated-English term list. Two defects: a `VERDITO`/`VEREDITO` typo in one plan's review block, and an inline-code placeholder identifier (`<category>` → `<categoria>`) translated when it shouldn't have been.

The reviewer-prompt translation explicitly keeps `**Verdict: APPROVE**` and `**Verdict: REQUEST CHANGES**` in English with an in-doc note that the orchestrator string-matches them. Worth flagging because that contract is invisible from the diff alone and a future translator could easily break it.

The compromise call from FEAT-006/007 is real: roughly 8-10 heavy-prose plan and design documents received only heading and bold-label translation, bodies untouched. The findings fields acknowledge this as a deliberate scope-control choice. The user's task says "translate every English Markdown file"; strict reading wants those bodies translated, lenient reading accepts the compromise for historical/superseded planning docs. Reviewer needs to make this call explicitly.
